# SkillHub 数据中台第一版需求理解与技术方案

## 文档目的

本文用于对齐第一版产品需求、系统边界和技术实现。它不是单纯的技术栈清单，也不描述尚未确定的远期架构。

第一版遵循以下原则：

- 避免过度设计和过度兜底。
- 采用成熟组件的最佳实践完成最小实现。
- 先解决已经明确的业务问题，再根据真实数据和使用反馈扩展。
- 模块保持高内聚、低耦合，但不提前建设抽象框架。

## 对需求的理解

### 项目目标

公司计划将广告营销能力制作成大量 Skill，分发到不同 Agent 生态。Skill 本身是用户可以获得的明文文件，因此不能把核心 Reference、热点数据和 KOC 达人资料直接打包到 Skill 中。

Skill 负责：

- 描述适用场景和工作流程；
- 指导 Agent 何时调用 MCP Tool；
- 提供公开说明和少量示例。

服务端负责：

- 保存和维护核心数据资产；
- 提供稳定的数据查询接口；
- 鉴别调用方并限制访问范围；
- 避免完整数据被直接下载或批量遍历。

调用关系如下：

```text
用户
  ↓
Agent 执行 Skill
  ↓
MCP Tool
  ↓
数据中台 REST API
  ↓
Reference / 热点 / KOC 数据
```

本项目是 SkillHub 背后的数据能力平台。第一版提供 REST API，由 MCP Server 调用；本项目暂不负责实现和分发 MCP Server。

### Skill 数据资产主干

第一版建设三类 Skill 数据能力：

```text
Skill
├── Reference 知识库
├── KOC 达人库
└── 品牌与趋势洞察（热点、行业趋势、品牌 GEO）
```

Reference 和 KOC 在业务上都是 Skill 使用的知识资产，但数据性质和查询方式不同：

| 数据 | 数据性质 | 来源 | 使用方式 |
| --- | --- | --- | --- |
| Reference | 非结构化或半结构化 | PDF、Word、Markdown 等运营文档 | 自然语言检索 |
| KOC | 结构化 | 运营提供的 Excel、CSV | 条件筛选 |
| 热点 | 结构化 | 第三方平台 API | 指标和趋势查询 |

文件格式不决定数据是否结构化。KOC 虽然通过“文档”上传，但表格中每行和每列有确定含义，因此属于结构化数据；Reference 即使被 Docling 转换成 JSON，其主要内容仍是需要语义检索的自然语言知识。

### 第一版业务边界

第一版包含：

1. Skill 元数据及其可使用的数据范围。
2. Reference 知识库、目录、文档上传、解析、切片和检索。
3. 统一 KOC 达人库、标准表格导入和结构化筛选。
4. 一个第三方热点数据平台的接入和统一查询。
5. 用户、API Key、调用鉴权和必要的审计信息。
6. 运营后台所需的管理接口。

第一版不包含视频生成、自动剪辑、TTS、数字人和爆款视频处理。这些是工具执行能力，不属于当前数据中台主干。

## 用户与使用场景

### 运营人员

运营人员通过内部后台：

- 创建和维护 Skill；
- 创建 Reference 知识库及目录；
- 上传文档并查看处理状态；
- 向统一 KOC 达人库导入标准表格；
- 查看 KOC 导入校验结果；
- 配置 Skill 可以使用的 Reference、KOC 和热点数据能力；
- 查看热点数据同步状态。

### Skill 与 MCP

Skill 通过 MCP Tool 使用数据中台：

- 根据问题检索 Reference；
- 根据明确条件筛选 KOC；
- 查询抖音、小红书热点指标。

Agent 不需要理解数据库 ID、Elasticsearch、COS 或第三方供应商字段。

## Skill 与数据范围

Skill 使用稳定且唯一的 `skill_key`，不使用可能改变或重复的展示名称。`skill_key` 用于路由数据范围，不作为鉴权凭证；鉴权仍由 API Key 负责。

第一版运营界面中，Reference 分组默认使用对应 Skill 的展示名称，让运营能直观看出主要用途。这只是命名约定，不是数据约束：Reference 与 Skill 仍通过独立关联表绑定，名称可以分别修改，一个 Reference 可以被多个 Skill 使用，一个 Skill 也可以使用多个 Reference。

一个 Skill 可以关联多个 Reference 分组，并分别绑定统一 KOC 达人库和所需的品牌洞察能力。第一版使用三套明确关系：

```text
skill_knowledge_base
- skill_id
- knowledge_base_id

skill_koc_access
- skill_id

skill_insight_capability
- skill_id
- capability_key
```

`skill_insight_capability` 按业务能力绑定，不做笼统的“全部洞察”，也不细化成 11 个接口逐个授权。第一版只提供 6 个清晰选项：

- 热门关键词：`get_hot_keywords`、`get_keyword_trend`、`get_related_keywords`；
- 飙升关键词：`get_rising_keywords`；
- 热门话题：`get_hot_topics`；
- 热门内容：`get_hot_content`、`get_content_format_trends`、`get_hot_creators`、`get_trend_detail`；
- 行业趋势：`get_category_trends`；
- 品牌 GEO：`get_brand_geo_insight`。

这样运营能按 Skill 的实际用途选择能力，接口增减时也不需要修改 Skill 的绑定模型。

`skill_koc_access` 同样以记录是否存在表示 Skill 能否使用 KOC 筛选能力。KOC 不分知识库；平台、行业、地区和粉丝范围只是统一达人库的查询条件。

暂不设计 `resource`、`dataset`、`resource_binding` 等万能资源模型，也不把第三方供应商当作 Skill 直接绑定的对象。供应商更换属于热点模块内部实现，不影响 Skill 的绑定关系和 Tool 契约。

## 第一版接口理解

### 接口原则

- 一个 Tool 解决一种明确问题，不设计万能查询接口。
- Agent 只填写业务参数，不填写检索阈值、索引名、数据库 ID 等内部参数。
- 返回数量、检索策略和最大时间范围由服务端控制。
- 第一版不使用 LLM 改写结果，由调用方 Agent 自行理解和组织数据。
- 不提供 Elasticsearch、COS 和第三方供应商的透传接口。

接口分为两层：

```text
Skill → MCP Tool → 数据中台 REST API
```

- MCP Tool 名称面向 Agent，表达可以完成的业务任务。
- REST API 由本项目实现，供 MCP Server 调用。
- 第一版业务查询统一使用 `POST` 和 JSON 请求体，避免把复杂筛选条件编码到 URL。
- 第一版共 13 个业务查询接口：1 个 Reference、1 个 KOC、10 个热点指标接口和 1 个品牌 GEO 接口。

这里的 13 个接口只统计 MCP 使用的业务查询。知识库、目录、文档上传、KOC 导入等运营后台 CRUD 属于内部管理接口，实施时按页面需求设计，不作为 Skill 能力对外宣传。

### Reference 检索

```text
MCP Tool: search_reference
REST API: POST /api/v1/references/search
```

请求：

```json
{
  "skill_key": "xiaohongshu_topic",
  "query": "母婴行业适合做什么内容"
}
```

响应：

```json
{
  "results": [
    {
      "title": "小红书母婴选题方法",
      "content": "优先从喂养、睡眠和家庭协作等高频问题中选择具体场景……"
    }
  ]
}
```

服务端根据 `skill_key` 确定知识库范围。`top_k`、阈值和检索方式由服务端固定。

第一版不会向外提供：

- 完整原始文档；
- COS 地址和内部文件路径；
- Elasticsearch 原始查询能力；
- 无限制分页和批量导出；
- Embedding、检索分数和内部索引信息。

系统仍会返回完成任务所需的少量相关片段。只要 Agent 需要使用知识，就无法做到完全不传递内容；第一版保护的重点是避免完整、直接和批量暴露。

### KOC 筛选

KOC 使用独立的结构化查询 Tool：

```text
MCP Tool: search_koc
REST API: POST /api/v1/koc/creators/search
```

```json
{
  "skill_key": "xiaohongshu_koc_selection",
  "platform": "xiaohongshu",
  "category": "母婴",
  "region": "上海",
  "min_followers": 10000,
  "max_followers": 100000
}
```

`skill_key` 和 `platform` 必填，其余条件可选。服务端确定知识库范围、返回数量和排序规则。

第一版返回业务所需字段，例如达人名称、平台、主页链接、粉丝数、地区、分类和标签，不返回内部记录、原始导入文件或无限分页结果。服务端根据 `skill_key` 校验 KOC 能力绑定，不需要选择知识库。

### 热点指标

第一版假设第三方平台能够提供抖音和小红书所需数据。本项目不开发爬虫，只负责供应商调用、字段标准化、必要存储和稳定查询。

计划提供以下十类业务指标接口：

| MCP Tool | REST API | 用途 |
| --- | --- | --- |
| `get_hot_keywords` | `POST /api/v1/trends/hot-keywords` | 当前热门关键词 |
| `get_rising_keywords` | `POST /api/v1/trends/rising-keywords` | 快速上升的新词 |
| `get_hot_topics` | `POST /api/v1/trends/hot-topics` | 热门话题或挑战 |
| `get_hot_content` | `POST /api/v1/trends/hot-content` | 热门视频或笔记 |
| `get_category_trends` | `POST /api/v1/trends/category-trends` | 行业整体走势 |
| `get_keyword_trend` | `POST /api/v1/trends/keyword-trend` | 单个关键词时间序列 |
| `get_related_keywords` | `POST /api/v1/trends/related-keywords` | 关联词和选题方向 |
| `get_content_format_trends` | `POST /api/v1/trends/content-format-trends` | 流行内容形式 |
| `get_hot_creators` | `POST /api/v1/trends/hot-creators` | 近期热点达人 |
| `get_trend_detail` | `POST /api/v1/trends/details` | 单个热点完整指标 |
| `get_brand_geo_insight` | `POST /api/v1/insights/brand-geo` | 品牌 GEO 排名、可见度和优化项 |

常用参数保持一致：

```json
{
  "skill_key": "xiaohongshu_topic",
  "platform": "xiaohongshu",
  "category": "母婴",
  "period": "7d"
}
```

- `skill_key` 必填。服务端先确认该 Skill 已绑定热点数据能力，未绑定则拒绝调用。
- `platform` 为 `douyin` 或 `xiaohongshu`。
- `category` 可选，使用平台维护的标准分类。
- `period` 使用有限枚举，例如 `1d`、`7d`、`30d`。
- `keyword`、`trend_id` 只出现在需要它们的接口中。

最终开放哪些指标以供应商真实字段为准。缺少可靠数据的指标不返回推测值，也不通过 LLM 补全。

`get_hot_creators` 表示第三方数据中的近期热点达人，不等同于运营维护的 KOC 达人库，两者第一版不合表。

品牌 GEO 查询使用 `skill_key`、`platform` 和 `brand` 三个必填参数，返回品牌在指定平台的 GEO 排名、可见度、品牌提及覆盖、内容覆盖和少量明确优化项。例如查询“可复美在小红书的 GEO 排名以及需要优化的地方”。第一版只返回第三方平台能够提供或可以确定计算的数据，不使用 LLM 虚构评分或建议。

## 技术方案

### 总体架构

```text
运营后台 / MCP Server
        ↓
      FastAPI
        ↓
┌────────────┬────────────┬────────────┐
│ Reference  │    KOC     │   Trends   │
└─────┬──────┴──────┬─────┴──────┬─────┘
      ↓             ↓            ↓
COS + Docling   PostgreSQL   第三方 API
      ↓                          ↓
Elasticsearch              PostgreSQL
```

第一版保持一个 FastAPI 单体应用和一个独立 Worker，不拆微服务。

### 技术栈

| 领域 | 选择 | 用途 |
| --- | --- | --- |
| Web API | FastAPI | 内部管理和对外 REST API |
| 接口认证 | API Key | 识别 MCP 调用方并控制访问 |
| 数据模型 | SQLModel | 模型定义和常规增删改查 |
| 业务数据库 | PostgreSQL | 用户、Skill、KOC、热点和处理状态 |
| 数据库迁移 | Alembic | 数据库结构版本管理 |
| 对象存储 | 腾讯云 COS | 原始文件和解析产物 |
| 文档解析 | Docling Serve | PDF 和常用 Office 文档解析 |
| 文档切片 | Docling HybridChunker | 按文档结构生成检索片段 |
| 搜索引擎 | Elasticsearch | Reference 关键词、向量和混合检索 |
| ES 客户端 | `elasticsearch-py` | Elasticsearch 索引和查询 |
| Embedding | 一个确定的 HTTP 模型服务 | 文档片段和查询向量生成 |
| 表格导入 | Python CSV 标准库、openpyxl | KOC CSV 和 Excel 导入 |
| 后台处理 | 独立 Worker | 文档解析、索引和表格导入 |
| 本地运行 | Docker Compose | 启动应用和依赖服务 |
| Python 管理 | uv | 依赖管理和版本锁定 |
| 代码检查 | Ruff、Mypy、Ty、pre-commit | 格式化和静态检查 |

第一版只接入一个确定的 Embedding 服务，不建设模型管理系统，也不接入回答大模型。

### 存储职责与决策

三种存储各自只承担一种主要职责：

| 存储 | 定位 | 适合保存 | 不负责 |
| --- | --- | --- | --- |
| PostgreSQL | 业务事实库 | 关系、状态和需要精确查询的结构化数据 | 大文件、文档正文、向量检索 |
| COS | 文件事实库 | 原始文件和体积较大的解析产物 | 条件筛选、关系查询、全文检索 |
| Elasticsearch | 可重建的检索索引 | Reference 切片、向量及检索字段 | 业务主数据、原始文件、唯一备份 |

PostgreSQL 和 COS 保存系统的事实数据；Elasticsearch 只保存由这些事实数据加工出的索引。Elasticsearch 数据丢失时，应能根据 PostgreSQL 中的文档记录和 COS 中的解析产物重新建立索引。

具体存储决策：

| 数据 | 存储位置 | 原因 |
| --- | --- | --- |
| 用户、API Key、Skill 及关联关系 | PostgreSQL | 需要事务、唯一约束和关系查询 |
| Reference 知识库、目录、文档元数据和状态 | PostgreSQL | 属于业务主数据，不包含文档正文 |
| Reference 原始文档 | COS | 文件体积不适合写入数据库，需要保留原始依据 |
| DoclingDocument JSON | COS | 是可重新切片的主要解析产物，体积可能较大 |
| Markdown 预览 | COS | 只供运营预览和人工检查，不参与业务关系查询 |
| Reference 切片、向量和检索字段 | Elasticsearch | 用于关键词、向量和混合检索，可重新生成 |
| KOC 原始 Excel/CSV | COS | 保留运营提供的原始数据，便于追溯和重新导入 |
| KOC 导入记录和达人记录 | PostgreSQL | 统一存储，按平台、分类、地区和粉丝数筛选 |
| 热点标准化数据和同步时间 | PostgreSQL | 第三方数据为结构化指标，需要稳定查询和排序 |

第一版明确不这样存：

- 不把文件二进制、完整 Markdown 或 Docling JSON 写入 PostgreSQL。
- PostgreSQL 只保存 COS `object_key`，不保存临时下载 URL。
- 不在 PostgreSQL 和 Elasticsearch 中重复保存一份完整 Reference 正文。
- 不把 KOC 表格切片后写入 Elasticsearch。
- 不把热点指标作为非结构化文本写入 Elasticsearch。
- 不把 Elasticsearch 当作业务数据库或数据备份。
- 不长期保存第三方热点 API 的原始响应；第一版只保存统一后的业务字段、来源和同步时间。

如果后续热点数据出现大规模全文搜索需求，再为热点建立独立 Elasticsearch 索引；这不是第一版默认设计。

### 模块划分

```text
app/modules/
├── auth/          登录认证
├── users/         用户管理
├── api_keys/      MCP 调用凭证
├── skills/        Skill 元数据和数据范围
├── files/         文件上传、校验和 COS
├── knowledge/     Reference 知识库、目录和文档
├── retrieval/     Elasticsearch 索引与检索
├── koc/           KOC 达人导入和筛选
├── trends/        第三方热点接入和查询
└── system/        健康检查
```

模块边界：

- `files` 只管理文件，不解析业务内容。
- `knowledge` 管理非结构化 Reference。
- `retrieval` 是内部能力，不提供直接访问 Elasticsearch 的公共接口。
- `koc` 负责 KOC 表格校验、导入和查询。
- `trends` 负责热点供应商接入、标准化和查询。
- 模块通过公开 Service 调用，不直接修改其他模块的数据。

第一版不建立 `infrastructure`、`processing`、通用 `integrations` 等目录。代码实际增长后再拆分。

## 核心数据结构

只保留第一版需要的业务实体：

```text
skill
knowledge_base
skill_knowledge_base
folder
document
skill_koc_access
koc_import
koc_creator
api_key
```

热点数据表根据供应商实际字段建立，不提前设计一个可以容纳所有指标的万能表。

目录只服务运营后台管理，不参与 MCP 参数，也不写入 Elasticsearch。移动文档目录不会影响检索。

## Reference 处理流程

```text
上传原文件到 COS
    ↓
创建 document，状态为 pending
    ↓
Worker 调用 Docling
    ↓
DoclingDocument JSON 和 Markdown 预览写入 COS
    ↓
HybridChunker 切片
    ↓
生成 Embedding
    ↓
Bulk 写入 Elasticsearch
    ↓
document 更新为 ready
```

Docling 使用原则：

- `DoclingDocument JSON` 是主要解析产物，Markdown 只用于预览。
- 使用 `HybridChunker`，不对 Markdown 做固定字符切片。
- Chunker 使用与 Embedding 模型匹配的 tokenizer。
- 只开启实际需要的 OCR、表格和图片能力。
- 暂不接入 MinerU；真实失败样本证明 Docling 不满足要求后再评估。

Elasticsearch 第一版只建立一个 Reference 切片索引，使用固定 Mapping 和 Bulk API。最小字段为：

```text
chunk_id
knowledge_base_id
document_id
content
embedding
section_path
page_numbers
```

## KOC 导入流程

第一版要求运营使用统一 Excel/CSV 模板：

```text
平台 | 达人名称 | 主页链接 | 粉丝数 | 地区 | 分类 | 标签
```

分类和标签允许多个值。第一版不识别任意 Word/PDF，不猜测列名；不符合模板时返回明确的行号和错误原因。

```text
上传 Excel/CSV 到 COS
    ↓
创建 koc_import，状态为 pending
    ↓
Worker 校验表头和每行数据
    ↓
有效记录写入 PostgreSQL
    ↓
记录成功数、失败数和错误原因
    ↓
koc_import 更新为 ready 或 failed
```

第一版不建设达人画像、智能评分、报价模型、粉丝画像和历史趋势模型。

## 现有 Docling 代码重构要求

当前 Docling 代码来自原 AI 聊天项目，围绕“用户上传附件后立即提取文本供对话使用”设计，不能直接扩展为知识库链路。

重构要求：

- `files` 模块不再调用 Docling。
- 上传完成只表示原文件可用，上传接口不等待解析。
- 解析失败不能删除已经上传成功的原文件。
- Docling 由 Worker 异步调用，失败后复用原文件重试。
- 移除 `stored_file.extracted_text` 和 `get_extracted_text` 等聊天附件设计。
- 解析结果写入 COS，不把完整 Markdown 写入 PostgreSQL。
- 解析任务只关联 `document_id`，不关联 Conversation、Message、Agent 或 Prompt。
- Reference 文档进入 Docling；KOC Excel/CSV 进入结构化导入，不经过 Docling。
- 删除 Reference 文档时，同时清理原文件、解析产物和 Elasticsearch 切片。
- 不保留旧聊天处理链路的兼容层。

职责调整为：

```text
files       上传、校验、COS
knowledge   文档记录和处理状态
worker      Docling 解析和产物保存
retrieval   切片、Embedding、Elasticsearch
koc         Excel/CSV 校验和结构化导入
```

## 后台处理

文档解析、索引和 KOC 导入不能阻塞上传请求，因此保留一个独立 Worker。

第一版使用 PostgreSQL 状态领取待处理记录，不引入 Redis、Celery 或 Kafka：

```text
pending → processing → ready
                    ↘ failed
```

第一版不实现任务优先级、复杂自动重试和分布式调度。热点需要定时同步时，由部署环境的定时任务调用同步命令，不引入调度平台。

## 第一版不做

- MCP Server 的实现和分发；
- LLM 回答生成和内容审核链路；
- 视频生成、自动剪辑、TTS 和数字人；
- 自研抖音、小红书爬虫；
- LangChain、LlamaIndex 和 Agent 框架；
- MinerU 和多解析器切换；
- 多 Embedding Provider 管理；
- Redis、Celery、Kafka；
- 独立向量数据库；
- 热点 Elasticsearch 索引；
- KOC 智能评分和画像系统；
- 微服务拆分；
- 万能资源模型、Protocol、工厂和插件系统。

## 当前假设与待确认项

以下事项不影响第一版架构，但实施前需要确定具体值：

1. 第三方热点供应商及其真实字段、更新频率和调用限制。
2. 第一版实际开放的热点指标接口。
3. KOC 标准模板的最终列和必填规则。
4. Embedding 模型、向量维度和匹配 tokenizer。
5. API Key 与调用方、Skill 数据范围的具体配置方式。

没有真实依据前，不为这些变化提前设计多供应商或动态模型框架。

## 第一版验收标准

- 运营可以创建 Skill、Reference 知识库和目录。
- 运营可以上传真实文档并查看解析和索引状态。
- 使用 `skill_key` 和问题可以检索 Skill 关联的 Reference。
- 外部接口不提供完整文档、COS 地址和 Elasticsearch 访问能力。
- 删除 Reference 文档后，其原文件、解析产物和索引内容得到清理。
- 运营可以通过标准 Excel/CSV 向统一 KOC 达人库导入数据。
- KOC 导入可以显示成功、失败数量和明确错误原因。
- 已绑定 KOC 能力的 Skill 可以通过结构化条件筛选统一达人库。
- 可以从一个确定的第三方平台同步抖音、小红书热点数据。
- 可以根据供应商实际字段提供确定的热点指标接口。
- 失败的文档处理和 KOC 导入可以复用原文件人工重试。

没有直接服务于以上验收标准的组件，不加入第一版。
